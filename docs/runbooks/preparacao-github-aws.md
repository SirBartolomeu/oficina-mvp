# Preparação manual para a apresentação GitHub/AWS

Execute na ordem. O assistente prepara Terraform, workflows e extração dos repositórios; os passos abaixo dependem da sua conta ou de autorização explícita. Não envie senhas, tokens ou chaves pelo chat e não os comite.

## 0. Acesso temporário na máquina da demo

1. Instale o [AWS CLI v2 para Windows](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html), se `aws --version` ainda não funcionar. O instalador oficial para o usuário atual não exige administrador. Abra um novo PowerShell depois da instalação.
2. Se sua conta usa IAM Identity Center, obtenha com o administrador a **Start URL**, a região do Identity Center e o permission set da conta. Configure e entre com:

   ```powershell
   aws configure sso --profile oficina-demo
   aws sso login --profile oficina-demo
   $env:AWS_PROFILE = 'oficina-demo'
   aws sts get-caller-identity --query '{Account:Account,Arn:Arn}'
   ```

   [Guia oficial do SSO no CLI](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html). Se a conta não usa Identity Center, use o perfil temporário aprovado pelo administrador e execute os dois últimos comandos com o nome desse perfil. Não copie access keys para o chat, Terraform ou GitHub Actions. O retorno de `get-caller-identity` pode ser compartilhado: contém ID da conta e ARN, sem segredo.
3. Confirme que o ID retornado é a conta da apresentação. Execute `terraform version` e `git --version`; o ZIP da Auth usa .NET 10. Mantenha o mesmo `$env:AWS_PROFILE` no terminal que executará `terraform init/plan/apply` e os comandos `aws s3`. Se a sessão expirar, repita `aws sso login --profile oficina-demo`.
4. O GitHub CLI está instalado nesta máquina. Em um novo PowerShell, faça login interativo na sua conta e confirme o owner antes de publicar:

   ```powershell
   gh auth login --web --hostname github.com --git-protocol https
   gh auth status
   gh api user --jq .login
   ```

   Não envie o token ao assistente. Se `gh` ou `aws` não forem reconhecidos após a instalação, abra um novo terminal para atualizar o `PATH`. Em 16/11/2026, os binários locais responderam `gh 2.104.0` e `aws-cli/2.40.2`; não havia login GitHub nem perfil AWS configurado.
5. Execute `./scripts/aws-demo/check-preconditions.ps1` na raiz do projeto. Ele lê apenas CLIs, perfis locais, seis clones e metadados de entrega; retorna código 1 enquanto houver pendências. A checagem não substitui `sts get-caller-identity`, revisão de custo, `terraform plan` ou runs reais do GitHub.

## 1. Conta, região e orçamento

1. Entre na conta AWS que usará na apresentação e escolha **uma região** para todos os recursos. Anote somente o ID da conta (12 dígitos) e a região, sem chaves.
2. Em **Billing and Cost Management → Budgets → Create budget**, crie um orçamento mensal pequeno, com alerta por e-mail para o valor que você aceita gastar. Budget **avisa, não impede gastos**; confirme o e-mail e monitore o painel. [Passos oficiais AWS](https://docs.aws.amazon.com/cost-management/latest/userguide/bcm-lite-create-a-budget.html).
3. Confirme que você tem permissão temporária para criar IAM OIDC, EC2, ECR, RDS, DynamoDB, SQS, VPC, S3, Secrets Manager e orçamento. Se for conta de organização, peça ao administrador essas permissões. O `terraform plan` apontará a lista concreta.
4. Informe ao assistente **região, ID da conta, teto de gasto e janela da apresentação**. O backend remoto precisa de um bucket S3 privado de estado, com versionamento, criptografia e bloqueio de acesso público; autorize sua criação antes do primeiro `terraform init` remoto. Os módulos novos usam `infra/aws-data/backend.hcl.example` e `infra/aws-k3s/backend.hcl.example`, com chaves `data.tfstate` e `k3s.tfstate` no mesmo bucket. Copie cada exemplo para `backend.hcl` ignorado e preencha bucket/região, sem chaves. Autentique o CLI por SSO/profile temporário. Antes de validar/planejar K3s, execute `./scripts/aws-demo/build-auth-lambda.ps1 -OutputPath infra/aws-k3s/artifacts/oficina-auth.zip`. Planeje/aplique **data antes de K3s**; revise recursos e custo antes de cada `apply`. Uma hora de apresentação não inclui a criação/migração do RDS.

## 2. Repositórios e GitHub Actions

1. Escolha owner e nomes para `oficina-os`, `oficina-execution`, `oficina-billing`, `oficina-auth-lambda`, `oficina-k8s-infra` e `oficina-data-infra`. Informe se serão privados. Os seis clones locais estão em `exports/`, preservam histórico Git, têm branch `main` e não têm remote. `./scripts/export-service-repos.ps1` e `./scripts/export-infra-repos.ps1` permitem recriar clones em outro diretório, mas recusam sobrescrever destinos existentes. Ajuste os nomes e `github_repositories`/`github_auth_repository` no Terraform se necessário. Autorize expressamente a publicação antes de criar repositórios remotos.
2. Após a publicação dos serviços, em cada repositório abra **Actions** e rode manualmente `os-ci`, `execution-ci` ou `billing-ci`. Os clones já mantêm os caminhos usados pelos workflows; testes unitários, integração PostgreSQL/DynamoDB/SQS, gates de cobertura de 80% nos três serviços e builds Docker passaram localmente. O runner do GitHub inicia os emuladores em contêineres e anexa os XML. Salve URL e captura de cada run verde. `phase4-local` e `deploy-kind` ainda pertencem somente ao repositório original; só estarão disponíveis no GitHub se esse repositório também for publicado com autorização.
3. Em **Settings → Rules → Rulesets**, crie regra para `main`: exigir pull request, checks CI verdes e bloquear force push. O nome do job dos três workflows é `test-and-image`; exija o check correspondente no repositório certo depois que ele aparecer pela primeira vez. Os três workflows executam em todo PR para `main`, inclusive mudanças só de README/manifests, para o check obrigatório não ficar pendente por filtro de caminhos. Confirme a regra com um PR de teste. [Regras oficiais GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets); [checks pulados por filtros](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs).
4. O Terraform define uma role OIDC por serviço, restrita ao owner/repo/branch `main`. Depois da aplicação autorizada, configure **Actions variables** em cada repositório: `AWS_REGION` e `K3S_INSTANCE_ID` nos três; `AWS_ROLE_ARN_OS`, `ECR_REPOSITORY_OS`, `SSM_DOCUMENT_OS` no OS; os equivalentes `_EXECUTION` e `_BILLING` nos demais. Os valores vêm dos outputs `k3s_instance_id`, `github_ecr_push_role_arns`, `ecr_repository_names` e `ssm_deploy_document_names`; não use a URI ECR completa como nome. Verifique o subject/branch na trust policy. [Orientação oficial AWS sobre GitHub OIDC](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html). Não criar `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` no GitHub. Quando faltarem variáveis, o workflow avisa e não publica/deploya.
5. No repositório Auth, configure `AWS_REGION`, `AWS_ROLE_ARN_AUTH` (output `github_auth_deploy_role_arn`) e `AUTH_LAMBDA_NAME` (output `auth_lambda_name`). O workflow `auth-ci` testa, empacota ZIP e atualiza somente o código da Function; o Terraform continua dono de VPC, IAM, API Gateway e configuração. Rode o workflow apenas após o `apply` autorizado e salve seu run verde.
6. Em **Settings → Collaborators and teams**, adicione `soat-architecture` nos seis repositórios, confirme o aceite/acesso e registre a evidência sem expor dados privados. Os READMEs devem conter propósito, tecnologia, execução/deploy, diagrama e link Swagger/Postman quando aplicável. Registre os seis links e a documentação em `docs/submission-metadata.json`; a entrega acadêmica exige essa confirmação no PDF.
7. Nos dois repositórios de infraestrutura, configure `AWS_REGION`, `AWS_STATE_BUCKET`, `GITHUB_OWNER` (K3s) e as roles OIDC de bootstrap `AWS_ROLE_ARN_INFRA_DATA`/`AWS_ROLE_ARN_INFRA_K3S`. Essas roles precisam existir antes do primeiro deploy pelo Actions e permitir apenas os recursos de cada módulo mais leitura/escrita na chave de state correspondente; K3s também lê `data.tfstate`. Crie o ambiente GitHub `aws-demo` com **revisores obrigatórios**. Os workflows sempre executam `fmt`/`validate`; `workflow_dispatch` com `deploy=true` gera `plan.txt` como artefato, aguarda aprovação do ambiente e só então aplica o plano salvo. Comece pelo repositório de dados, depois K3s. Não dispare `deploy=true` sem autorização explícita para os recursos pagos.

Para validar o ZIP no clone Auth desta máquina, execute `./scripts/aws-demo/build-auth-lambda.ps1 -DotnetPath C:\projects\oficina-mvp\.dotnet_home\sdk10\dotnet.exe` dentro de `exports/oficina-auth-lambda`; em uma máquina com .NET 10 instalado normalmente, omita `-DotnetPath`.

## 3. Credenciais externas e deploy

1. Se houver tempo e conta Mercado Pago de testes, obtenha Access Token e segredo de webhook **de testes** e configure-os no AWS Secrets Manager apenas após a infraestrutura existir. O callback precisa de URL HTTPS pública confiável. Sem isso, apresentar o pagamento simulado e dizer claramente que a transação externa não foi testada.
2. Revise os planos **data** e **K3s** separadamente e autorize explicitamente cada `apply` nessa ordem; não aplique `infra/aws-demo` no mesmo ambiente, pois ele duplicaria os recursos. Depois valide no console: EC2/K3s, RDS, tabela DynamoDB, três filas SQS com DLQ e três repositórios ECR. Em **EC2 → Instances → Connect → Session Manager**, entre no nó e execute `sudo k3s kubectl get nodes` e `sudo k3s kubectl -n oficina get pods,svc,hpa`. O security group não abre SSH; a existência dos recursos não prova que os pods estão prontos. Confirme readiness dos três serviços e smoke do fluxo.
3. Após `apply` autorizado, configure primeiro apenas `AWS_REGION`, `AWS_ROLE_ARN_*` e `ECR_REPOSITORY_*` no GitHub. Rode os três workflows em `main` para publicar as primeiras imagens ECR; o deploy SSM será pulado com aviso porque ainda não há Deployments. Na máquina local, execute `./scripts/aws-demo/package-deployment.ps1 -TerraformDirectory infra/aws-k3s`; ele lê outputs do Terraform, produz `%TEMP%\oficina-demo-assets.tar.gz` e mostra SHA256. Consulte `terraform -chdir=infra/aws-k3s output -raw deployment_assets_bucket` e envie o pacote ao caminho `s3://BUCKET_DO_OUTPUT/demo/assets.tar.gz` com `aws s3 cp`. No nó K3s via Session Manager, execute `aws s3 cp s3://BUCKET_DO_OUTPUT/demo/assets.tar.gz /tmp/oficina-assets.tar.gz`, `sha256sum /tmp/oficina-assets.tar.gz` e compare com o SHA256 local. Só então execute `sudo mkdir -p /opt/oficina-demo`, `sudo tar -xzf /tmp/oficina-assets.tar.gz -C /opt/oficina-demo` e `bash /opt/oficina-demo/scripts/aws-demo/initial-deploy.sh`. O script injeta região, tabela e URLs das filas a partir dos outputs, sem editar os manifests no Git, e termina testando os três endpoints `/health/ready` por `port-forward` local. Execute no nó `bash /opt/oficina-demo/scripts/aws-demo/verify-flow-k3s.sh`; ele cadastra o cliente de demonstração se necessário, cria uma OS, comprova cotação Execução → orçamento Billing → `AwaitingApproval` e testa CPF → JWT na Lambda → tracking protegido. A Lambda lê o segredo da OS por endpoint privado após o bootstrap. O script imprime ID e trace sem exibir credenciais. Depois, configure `SSM_DOCUMENT_*` e `K3S_INSTANCE_ID` e rode novamente cada workflow em `main` para comprovar o CD via SSM. Guarde URL do run, SHA de cada imagem, `kubectl`/healthchecks e um trace/OS real. A demonstração local em `docs/evidence/demo-local.json` é evidência complementar.

## 4. Apresentação e encerramento

Pouco antes dos 15 minutos, no nó K3s via Session Manager, execute `bash /opt/oficina-demo/scripts/aws-demo/refresh-demo-credentials.sh`. Ele renova as credenciais STS dos três serviços, reinicia os Deployments e exige readiness HTTP; não repete o bootstrap do RDS nem altera senhas de banco. Prepare abas do GitHub Actions, console AWS e terminal K3s. Use `docs/demo-15-min.md` como roteiro. Após a gravação, revise `terraform -chdir=infra/aws-k3s plan -destroy` e depois `terraform -chdir=infra/aws-data plan -destroy` com as mesmas variáveis usadas no apply e autorize explicitamente o `destroy` se os dados da demo puderem ser descartados. O módulo está preparado para remover ECR com imagens e o bucket de pacotes com objeto ainda presente; RDS não cria snapshot final e os segredos de aplicação são removidos sem recuperação. Confirme no console RDS, volumes EBS, IPv4, endpoint privado, ECR, S3 de pacotes e logs residuais, e consulte Cost Explorer no dia seguinte. O bucket **separado** do estado Terraform não é removido pelo módulo; decida depois se precisa conservar o state. Parar a EC2 sozinha não zera a conta.

## Ponto de decisão

Se conta, permissões, autorização de publicação e `apply` não estiverem disponíveis no início do segundo dia, use o demo Docker como prova executada. O deploy `kind` no GitHub Actions só pode ser mostrado se o repositório original também for publicado e o run for executado. Mostre Terraform apenas como configuração validada localmente e declare que o deploy AWS ficou pendente. Não substituir evidência real por captura simulada.
