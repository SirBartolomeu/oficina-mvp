# Terraform AWS da demonstração — em construção

O módulo define três ECR, três filas SQS com DLQ, uma tabela DynamoDB `PAY_PER_REQUEST`, VPC, subnet pública para um nó K3s, duas subnets privadas em zonas distintas e RDS PostgreSQL Single-AZ. O RDS só aceita PostgreSQL do security group K3s e usa senha mestre gerenciada pelo RDS/Secrets Manager. Não há NAT Gateway. A EC2 Amazon Linux 2023 instala K3s na primeira inicialização e pode ser acessada pelo Systems Manager; o security group não tem regra de entrada pública ou SSH. O IMDSv2 é obrigatório com hop limit 1 para não expor a role do host aos pods.

O módulo também cria o provedor OIDC do GitHub e três roles distintas, cada uma vinculada a `main` de um repositório e autorizada a publicar somente no ECR do próprio serviço. Os workflows de CI usam essas roles para enviar a imagem após testes/build em `main`, quando as variáveis GitHub estiverem configuradas. A role do host K3s tem Systems Manager, leitura das três imagens ECR e permissão para assumir três roles de workload. OS, Execução e Billing têm permissões separadas por fila; somente Billing acessa sua tabela DynamoDB. Se o provedor OIDC GitHub já existir na conta, ele precisa ser importado ao estado Terraform antes do `apply`.

Na janela da demo, `scripts/aws-demo/prepare-workload-credentials.sh` obtém credenciais STS de até uma hora por serviço e cria Secrets Kubernetes separados; ele também cria a credencial temporária de pull ECR. Os pods não acessam IMDS e leem apenas o Secret de sua role. O K3s habilita criptografia de Secrets em repouso. Depois do deploy inicial, execute `refresh-demo-credentials.sh` pouco antes da apresentação: ele renova as credenciais, reinicia os três Deployments e testa readiness, sem repetir o bootstrap do banco. Remova os Secrets ao encerrar. É uma solução de demonstração de um nó; para operação contínua, substituir a renovação manual por identidade de workload automatizada.

O Terraform também cria três entradas vazias no Secrets Manager. `scripts/aws-demo/bootstrap-rds-and-app-secrets.sh` cria os databases e usuários `oficina_os`/`oficina_execution`, grava senhas e tokens fora do Terraform state e prepara os Secrets Kubernetes de aplicação. O nó K3s pode ler o segredo mestre gerenciado pelo RDS e gravar apenas essas três entradas; a role do Billing continua sem acesso a segredos. A criação dos bancos e a distribuição de credenciais ainda não foram executadas em EC2 real.

A autenticação de cliente usa a Function .NET 10 `Oficina.Auth` em Lambda, exposta apenas em `POST /auth/token` por HTTP API com throttling. A Function entra nas subnets privadas e acessa a OS pelo NodePort 30080, permitido somente do security group da Lambda. Execute `scripts/aws-demo/build-auth-lambda.ps1` **antes** do `terraform plan`; o ZIP fica ignorado pelo Git. A Lambda lê o segredo da OS em runtime por um endpoint privado do Secrets Manager em uma AZ, permitido somente do seu security group. O Terraform guarda apenas o ARN e não grava chave JWT ou token de consulta no state. O timeout de 20 segundos e 512 MiB dão margem à primeira invocação .NET/VPC; o custo segue por uso. O endpoint gera custo horário até o `destroy` autorizado. Sem o bootstrap do segredo da OS, a rota retorna indisponibilidade; a Function mantém o segredo em memória na instância aquecida, então a rotação exige reciclar as instâncias da Lambda. Não há NAT.

Uma quarta role OIDC, restrita a `github_auth_repository` na `main`, permite ao workflow `auth-ci` somente atualizar o código da Function e consultar seu estado. O ZIP inicial continua vindo do build local antes do `terraform plan`; runs posteriores podem demonstrar o deploy serverless pelo GitHub Actions. Um novo `terraform apply` com ZIP local antigo pode reverter o código publicado pelo Actions, então reconstruir o ZIP local a partir do mesmo commit antes de aplicar novamente.

Três documentos SSM de deploy recebem somente um SHA Git válido, atualizam a imagem do Deployment correspondente e verificam o rollout. Cada role OIDC pode executar apenas seu documento no nó K3s e consultar o resultado. Os workflows de CI chamam esses documentos após publicar ECR. Para o primeiro deploy, um bucket S3 privado recebe um pacote curto de scripts/manifests (objetos expiram em dois dias); a role do nó pode somente ler `demo/*`. `scripts/aws-demo/package-deployment.ps1` gera o pacote a partir dos outputs do Terraform. Após o upload e conferência do SHA256, `initial-deploy.sh` verifica primeiro as três imagens ECR; só então prepara RDS/Secrets e injeta região, tabela, URLs SQS e imagens no Kustomize antes de aplicar.

Ainda faltam criar o bucket de estado autorizado, inicializar o backend remoto e executar upload/deploy/smoke reais; scripts e K3s não foram testados em EC2. **Não executar `apply`** antes do plan revisado e da autorização; nenhum recurso AWS foi criado.

O backend S3 está declarado, mas depende de um bucket privado criado fora deste módulo antes do primeiro `init` remoto. Copie `backend.hcl.example` para `backend.hcl` (ignorado pelo Git), escolha bucket/região e mantenha versionamento e bloqueio público no bucket. O lock usa um objeto `.tflock`, sem tabela DynamoDB adicional. A credencial local deve vir de AWS SSO/profile temporário; não usar access keys no arquivo. O bucket de estado permanece fora do `destroy` do ambiente e só deve ser removido após guardar ou descartar conscientemente o estado.

```powershell
terraform -chdir=infra/aws-demo fmt -check
terraform -chdir=infra/aws-demo init -backend=false
terraform -chdir=infra/aws-demo validate
./scripts/aws-demo/build-auth-lambda.ps1
terraform -chdir=infra/aws-demo init -backend-config=backend.hcl
terraform -chdir=infra/aws-demo plan -var='aws_region=REGIAO_ESCOLHIDA' -var='github_owner=SEU_OWNER'
```

O `plan` consulta a conta AWS configurada e só deve ser executado após a escolha da conta/região e nomes finais dos repositórios. Confirmar se `db.t4g.micro` e `gp3` estão disponíveis e o preço real da região escolhida. Não guardar credenciais ou `tfstate` no Git. Os nomes/URLs de saída alimentarão os manifests K3s. A política ECR retém cinco imagens por serviço; `force_delete` permite que um `destroy` **autorizado** remova os repositórios mesmo com imagens. O bucket de pacote também permite `force_destroy`, pois o objeto da demo pode não ter expirado. O RDS pula snapshot final e os três segredos são removidos sem recuperação em um eventual `destroy` autorizado; produzir backup se for necessário conservar dados antes desse ato. O bucket separado de estado Terraform permanece e precisa de decisão explícita depois do ambiente.
